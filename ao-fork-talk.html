2 — 簡介

什麼是 Agent Orchestrator？

Agent Orchestrator 是一個用來平行化管理多個 AI Agent 的開源調度層（Orchestration Layer）。當你有數十個 Issue 需要平行處理時，它可以自動為每個 Issue 建立獨立的工作區（Worktree）、指派 Agent 展開實作（讀程式、寫測試、發 PR），並自動處理 CI 失敗與 Review 意見的循環反饋。 

Jira (team UI)
  ↓ poll (REST API, 30s interval)
Orchestrator (~300 lines)
  ├── Jira Client (~200 lines) — fetchCandidates, fetchCurrentStates, fetchTerminalIssues
  ├── Agent Runner (~150 lines) — git worktree + claude -p + arcforge
  └── WORKFLOW.md — YAML config + prompt template
        ↓
Claude Code + arcforge (per-issue worktree)
  ├── arc-tdd, arc-verifying, arc-debugging
  ├── git push + open PR
  └── comment PR link on Jira issue
        ↓
CI (existing pipeline)
  ├── lint + test
  └── PR ready for human review

3 — 為什麼做這個修改版

原版的痛點與差異

在使用原版的 Agent Orchestrator 時，遇到了以下難題，因此決定做出客製化：

  1. 1
    實作衝突難以解決 不同的 Jira ticket 同時交給 Agent 實作時非常容易互相衝突（例如改到同份檔案）。 光是人工 review 解衝突就會卡住，特別是遇到非本人的實作，根本不知道怎麼 merge 或誰先誰後。
  2. 2
    額外支援 Jira 與解耦實作層 修改版額外支援了以 Jira 作為 Input，並把實作層獨立抽出來變成 pipeline 的一部分，藉此建立包含自動狀態同步的 workflow。

4 — 三階段 Pipeline

Phase 0 spec / Phase 1 整合 + 衝突偵測 / Phase 2 wave-by-wave impl，後兩段由 reaction 自動觸發。 
Phase 0 ─ Spec 產生
─────────────────────────────────────────────────────────────
   Dashboard       ── bulk spawn (N issues, type=spec) ──►  Spec Agents (×N)
   Spec Agents     ── 各自寫 specs/ISSUE.md, push feat/ISSUE
   Spec Agents     ── ao report completed ───────────────►  done state


Phase 1 ─ 規格整合（auto）
─────────────────────────────────────────────────────────────
   spec-phase-complete reaction 觸發
       │
       ├─►  gather-specs.mjs       收 spec 到主 repo + 釋放 worktree
       │
       └─►  conflict-detection.mjs union-find → 升冪 → blocked_by 注入
                                   ── 輸出 .claude/tasks/*.json (wave plan)
                                   ── 輸出 specs/conflict-report.json (audit)


Phase 2 ─ Wave-by-wave 實作（auto）
─────────────────────────────────────────────────────────────
   loop:
       wave-monitor    ── 確認上一 wave 全 merged
                       ── ao spawn ISSUE --session-type impl
                       ──────────────────────────────────►  Impl Agent
       Impl Agent      ── PR opened / CI / review / merged
                       ──────────────────────────────────►  Lifecycle Mgr
                       ──────────────────────────────────►  Jira comment

5 — 衝突處理

Conflict 自動序列化

兩份 spec 的 files_to_touch 一旦交集，pipeline 不再 abort，會自動把它們串成單一 chain，走原本的 wave plan 邏輯。

想保留平行： 把重疊檔從 spec frontmatter 拿掉即可。
  1. 偵測 files_to_touch 交集 → union-find 把所有重疊 issue 分成 connected components。
  2. Chain 內按 task id 升冪排序（A → B → C），自動取 issue id 數字部分。
  3. 注入隱含 blocked_by（B blocked by A、C blocked by B）。
  4. 走原本 DAG → wave plan 邏輯，輸出 .claude/tasks/*.json。
  5. 互不相關的群仍可平行；specs/conflict-report.json 留 audit log。

7 — 上手

Quick Start

最少 4 步讓 dashboard 跑起來。注意：用 AO_CONFIG_PATH，不要用 AO_GLOBAL_CONFIG（後者會把非 identity 欄位 strip 掉）。 

# 1. 安裝
$ git clone https://github.com/huskylin/agent-orchestrator
$ cd agent-orchestrator && pnpm install && pnpm build

# 2. Jira 認證
$ export JIRA_EMAIL=you@yourcompany.com
$ export JIRA_TOKEN=<jira-api-token>

# 3. 指定 config 路徑
$ echo 'export AO_CONFIG_PATH="$HOME/projects/agent-orchestrator/agent-orchestrator.yaml"' >> ~/.zshrc
$ source ~/.zshrc

# 4. 啟動 → http://localhost:3000
$ ao start

8 — 與上游的差異

Fork 加了什麼

[plugin]

tracker-jira

  • Jira Server REST API v2，支援 Sprint 篩選
  • Tracker 介面新增 addComment
  • 各狀態變化自動寫對應 comment 回 issue
[core]

Lifecycle 同步 + Dedup

  • PR open / merged / ci_failed 自動同步 Jira
  • trackerNotifiedStatus metadata + 跨 process file lock，避免雙觸發
  • Spec session 用 done terminal state（取代 idle）
[web · cli]

Dashboard 改動

  • IssuePanel：Sprint filter + 全選 + Spec Phase 批量按鈕
  • silence-rejection preload + instrumentation hook，吸 SSE controller-closed 暫態
  • 關掉 web 端 LifecycleManager 自動 polling，CLI worker 為唯一 poller
[scripts]

Spec-Phase Pipeline

  • phase0-spawn-specs：從 Sprint 批量產 spec session
  • gather-specs：收 spec、清掉 worktree、釋放分支
  • conflict-detection：union-find auto-serialise + audit log
  • wave-monitor：wave-by-wave 調度 impl agent
